## Baseline and scope

Starting `main` was `3f5d88a742345cf849ab90f6df884eefe4873062`, the merged plan PR #73.
Its [CI run 790](https://github.com/OhOkThisIsFine/llm-relay/actions/runs/35696057049) passed.
The published package remains v0.86.0. Separate documentation PR #72 was not incorporated here.

The reported lock race was real. In the baseline `src/storage/file-lock.ts` (blob
`afff818f1e0ff9fcc9a5a26978e728ea7d317970`), both reclamation and release recursively removed the
reusable lock path after checking its owner. A paused stale reclaimer could therefore delete a
replacement owner's live lock. Another owner check alone does not close that window.

## Reproduction and fix

`test/helpers/file-lock-race.ts` coordinates three real processes using explicit barriers:

1. Kill a holder after it acquires the actual repository lock, and wait for process exit.
2. Pause a reclaimer after its final owner read. Let another process reclaim and hold the replacement
   lock while its read/modify/write transaction is unfinished.
3. Resume the delayed reclaimer. Assert that it remains excluded until the replacement releases,
   that both transactions exit normally, and that both rows survive.

The unmodified baseline failed this sequence on Linux: the delayed process entered the critical
section while the replacement held it, one row was lost, and the replacement reported changed
ownership. The fixture intercepts filesystem calls only inside its child process; it does not
replace the lock implementation. A second barrier covers a delay after owner-marker retirement.

The fix publishes a complete version-2 claim with a unique `owner-<uuid>.json` marker. Reclamation
and release unlink only their own generation's marker, then use nonrecursive `rmdir`. A late unlink
cannot remove a successor's marker, and an empty-directory removal cannot remove a populated live
claim. Recovery of a dead new-format owner and a directory left empty during retirement remains
supported. Only an `ESRCH` liveness error establishes process absence; uncertainty fails closed.

## Initial contract classification

This is a reviewed starting slice, not an exhaustive inventory of the request and dispatch suites.

| Tests or area | Product guarantee to preserve | Replaceable implementation detail |
|---|---|---|
| MCP persistence concurrency | Non-conflicting mutations preserve every row; contention and owner death cannot admit overlapping writers | JSON journals, per-MCP PIDs and lock-directory format |
| JSON store transactions | Invalid existing data is not silently overwritten; read/modify/write is atomic and failures are surfaced | Rename retry plumbing and JSON serialization |
| New lock regressions | Mutual exclusion and both committed rows survive delayed reclamation | Version-2 marker names and the filesystem barrier locations |
| Kernel architecture | Explicit boundaries and no dependency cycles | Today's `src/kernel` placement and sibling-only import rule |
| Candidate-runner exports | No unnecessary public API | The old module's existence and a test requiring more than 50 exports |

Retain the behavioral concurrency regression at the store/service boundary when R3/R4 remove this
lock. Do not preserve the old lock module or obsolete export counts solely to keep structural tests
passing. Request-front, streaming, accounting, authorization and dispatch contracts still need the
plan's complete classification before their corresponding cutovers.

## Upgrade and deletion boundary

Drain and stop all old daemon, MCP and writing CLI processes before upgrading writers together.
Do not run old and new lock implementations concurrently during stale-lock recovery: an old
reclaimer already past its owner check can still perform the unsafe deletion.

Legacy `owner.json`, malformed and mismatched locks are not reclaimed automatically. For a legacy
timeout, first confirm all writers are stopped and the lock is stale, then remove only the adjacent
`.lock` directory. Preserve the protected state JSON and restart all writers on one version.
Do not treat elapsed lock age or a PID guess as sufficient authorization to remove it.

This is a temporary safety fix, not a new long-term persistence architecture. Delete the mechanism
and its format-specific tests once daemon ownership and transactional storage replace every writer;
carry the mutual-exclusion, no-lost-rows and crash-recovery guarantees into the replacement tests.
